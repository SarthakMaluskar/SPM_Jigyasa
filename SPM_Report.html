1. Main Objective of the Project and Real-World Problem It Solves

Objective: The main objective of Jigyasa is to provide a comprehensive, web-based platform for creating, distributing, managing, and analyzing online surveys. The system enables authenticated users to design customizable surveys, collect responses from target audiences, and perform data analysis with visualizations and exportable reports.

Real-world problem addressed: Many organizations, institutions, and researchers still rely on fragmented tools (paper forms, spreadsheets, or separate services) to gather feedback and analyze results. This leads to inefficiencies, data inconsistency, limited access control, and time-consuming manual analysis. Jigyasa solves these problems by offering:

  • Centralized survey lifecycle management: Create, edit, activate/deactivate, and share surveys from a single dashboard.
  • Controlled participation: Organization-linked users and surveys with optional organization-restricted access ensure responses come from the intended audience.
  • Structured response collection: Support for text, single-choice, and multiple-choice questions with required-field validation improves data quality.
  • Built-in analysis: CSV upload, interactive plotting (scatter, bar, line, pie, histogram, heatmap, box, area), grouping, saved analyses, and PDF export reduce the effort needed to derive insights.
  • Accessibility and scalability: A web-based interface allows creators and respondents to access surveys from anywhere, streamlining feedback collection for academic, organizational, and research use cases.

2. Choice of Technology Stack and Methodology

The project adopts a full-stack JavaScript (MERN-style) architecture with a modular, RESTful design. This stack was chosen for development efficiency, maintainability, and suitability for data-driven web applications.

Frontend:

  • React 18 + Vite: Component-based UI development, fast development server, and optimized production builds for a responsive single-page application.
  • Tailwind CSS: Utility-first styling for rapid, consistent, and maintainable UI design.
  • React Router: Client-side routing for dashboard, survey management, public response pages, and analysis views.
  • Axios: Centralized HTTP client for API communication with configurable base URL and timeouts.
  • Chart.js, React-Chartjs-2, Plotly.js, React-Plotly.js: Rich interactive data visualizations for survey and CSV analysis.
  • React Toastify & Lucide/React Icons: User feedback notifications and consistent iconography.

Backend:

  • Node.js + Express: Lightweight, non-blocking server ideal for REST APIs and I/O-bound operations (auth, CRUD, file uploads).
  • MongoDB + Mongoose: Flexible document schema for evolving survey structures (dynamic questions, choices, answers) and easy modeling of relationships.
  • JWT (jsonwebtoken) + bcryptjs: Stateless authentication and secure password hashing for user accounts.
  • Multer, csv/csv-parse/csv-parser, json2csv: File upload handling and CSV parsing/export for the data analysis workflow.
  • express-async-handler, CORS, dotenv: Clean async error handling, cross-origin access control for separate client/server deployment, and environment-based configuration.

Methodology: The system follows a client–server, layered/modular architecture (routes, controllers, models, middleware, utilities) and REST API conventions. This separation of concerns supports parallel frontend/backend development, easier testing, and incremental feature addition (e.g., survey management, responses, and analysis as distinct modules). Version control with Git and environment-driven configuration (development/production) support collaborative and deployable software project management practices.

3. System Architecture and Data Flow

Architecture overview: Jigyasa is a three-tier web application:

  • Presentation tier (Client): React SPA (Vite) served to users; handles UI rendering, form validation, routing, and visualization.
  • Application tier (Server): Express.js REST API exposing endpoints for authentication, organizations, surveys, survey responses, data analysis, and compatibility/public access routes. Middleware handles CORS, JSON parsing, request logging, no-cache headers for APIs, and centralized error handling.
  • Data tier: MongoDB database accessed via Mongoose models for users/profiles, organizations, surveys, questions/choices, responses/answers, and analysis-related data.

Key modules and routes:

  • /api/auth/* – registration, login, token/profile operations
  • /api/organizations/* – organization listing and management
  • /api/surveys/* – survey CRUD and listing
  • /api/survey-responses/* – submission and retrieval of responses
  • /api/data-analysis/* – CSV upload, plot/group operations, saving analyses
  • /api/api/* – public/compatibility endpoints (e.g., public survey access)
  • Health check: /api/health

Data flow (typical scenarios):

  • Authentication: User submits credentials via the React login/register forms → Axios sends request to /api/auth → server validates, hashes/verifies passwords, issues JWT → client stores token (e.g., access token) and attaches it in Authorization headers for protected requests.
  • Survey creation & management: Creator defines survey metadata and questions in the dashboard → client POST/PUTs to /api/surveys → controllers validate and persist survey/question/choice documents in MongoDB → updated data returned and rendered in survey list/detail/edit views.
  • Survey response submission: Respondent opens a public/survey link (/surveys/:creatorId/:surveyId) → client fetches survey definition via public API → user fills answers → client submits to /api/survey-responses → server validates required fields and organization constraints, stores response/answers → confirmation/thank-you page shown.
  • Data analysis: User uploads CSV in analyzer → Multer/server parses file and returns columns/metadata → user selects plot type and axes → client requests plot/group data from /api/data-analysis → server processes data and returns visualization-ready payload → Plotly/Chart.js renders charts; analyses can be saved and exported (e.g., PDF) for reporting.

The server uses per-request database connection handling (suitable for serverless deployment like Vercel) and serves static assets/health endpoints alongside the API.

4. Major Technical Challenges or Bugs Faced and How They Were Overcome

During development and deployment of a full-stack survey and analytics platform, several practical challenges typically arise. The following key challenges and mitigations are reflected in the project’s design and configuration:

  • Cross-origin communication between client and server: With the React frontend and Express API hosted separately, browsers block requests due to CORS policies. Resolution: Configured CORS middleware with environment-driven allowed origins, credentials, and permitted methods/headers to securely enable client–server interaction in development and production.
  • Secure authentication and session handling: Protecting user accounts and restricting access to survey management and responses required robust auth. Resolution: Implemented JWT-based stateless authentication with bcrypt password hashing, token configuration via environment variables, and protected API routes/middleware to ensure only authorized users access sensitive operations.
  • Dynamic and nested survey data modeling: Surveys contain varying numbers/types of questions (text, single/multiple choice) and nested choices/answers, making schema design and validation complex. Resolution: Used MongoDB/Mongoose’s flexible document modeling to represent surveys, questions, choices, responses, and answers, with server-side validation for required fields and question-type constraints.
  • CSV upload and data processing for analysis: Handling file uploads, parsing heterogeneous CSV data, and generating correct plot/group results can cause runtime and data-format issues. Resolution: Integrated Multer for uploads and CSV parsing libraries on the backend, with dedicated analysis endpoints to transform raw data into structured payloads consumable by Plotly/Chart.js on the frontend.
  • Deployment and environment configuration issues: Differences between local and production (API base URLs, database URIs, caching behavior, serverless constraints) can break functionality. Resolution: Externalized configuration using .env variables (API URLs, JWT secrets, MongoDB URI, CORS origin, etc.), added a health-check endpoint, applied no-cache middleware for API responses to avoid stale data on platforms like Vercel, and implemented reusable DB connection logic. Documentation (README/DEPLOYMENT) guides consistent setup.
  • API evolution/migration consistency: Project documentation indicates an earlier Django-based design reference and evolution to a Node/Express backend, which can introduce endpoint and data-contract mismatches. Resolution: Maintained modular routing (including compatibility routes) and a clear separation of concerns to align frontend expectations with backend APIs during iteration.

5. Key Limitations of the System and Future Scope

Key limitations:

  • Scalability and performance at large scale: Advanced optimizations such as pagination for very large survey/response datasets, caching layers, and background job processing for heavy analytics/PDF generation may be limited in the current implementation.
  • Limited question/logic complexity: The system supports core question types (text, single choice, multiple choice) but may lack advanced survey logic such as conditional branching/skip logic, question piping, and complex validation rules.
  • Analytics and reporting depth: While CSV analysis and multiple chart types are supported, advanced statistical analysis, real-time dashboards, and automated insight generation are not fully developed.
  • Security and compliance hardening: Further enhancements like fine-grained role-based access control (RBAC), audit logs, rate limiting enforcement, CAPTCHA for public forms, and compliance features (e.g., data retention policies) can be strengthened for enterprise use.
  • Testing and quality assurance: Comprehensive automated test coverage (unit, integration, end-to-end) and CI/CD pipelines may be limited, affecting regression detection during rapid changes.
  • User experience enhancements: Features such as multi-language support, accessibility (WCAG) refinements, offline/poor-network handling, and richer respondent experience can be improved.

Future scope:

  • Advanced survey features: Add conditional logic, sections/pages, timed surveys, file-upload questions, and customizable themes/templates.
  • Collaboration and sharing: Team-based survey authoring, role permissions (admin/creator/analyst/respondent), and shareable analytics dashboards.
  • Enhanced analytics & AI insights: Sentiment analysis for text responses, trend detection, automated summary reports, and export to multiple formats (Excel, PPT).
  • Integration and extensibility: Webhooks/APIs for third-party integrations (email, Slack, LMS/CRM), and scheduled survey distribution.
  • Performance and reliability: Implement pagination, indexing strategies, caching (e.g., Redis), background workers/queues, and monitoring/log aggregation for production reliability.
  • Mobile and omnichannel access: Develop a responsive PWA or dedicated mobile app and support QR-code-based survey distribution.
  • Security & compliance: Strengthen RBAC, audit trails, encryption at rest/in transit policies, and privacy controls to meet organizational or regulatory requirements.
